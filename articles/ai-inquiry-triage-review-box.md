問い合わせメールを AI で部署ごとに振り分けるとき、分類の選択肢を「内見」「修繕」「退去」のような業務カテゴリだけにしていませんか。その作り方だと、**どこにも当てはまらないメールや、人がすぐ読むべきメールも、AI はどれかの箱に入れてしまいます**。

不動産会社に届きそうなメール40通（架空）を Codex CLI で480回分類しました。業務カテゴリ7つだけで分類させると、「弁護士に相談して家賃も止めます」というクレームは**2モデル×2回の4回すべてで「入居中の不具合・修繕」**に、空室対策の広告の営業メールは**4回すべてで「空室・条件の問い合わせ」**に入りました。選択肢に「要確認」を1つ足すと、あいまいなメール10通×2回のうち **gpt-6-luna は15/20、gpt-6.1-terra は18/20** を人の確認に回し、はっきりしたメール30通×2回は**どの条件でも60/60正解、誤って人に回したのは0回**でした。（確認日: 2026-10-30）

![古い農家の作業小屋で、収穫したりんごが種類ごとに木箱へ分けられ、横の小さな竹かごにだけ、手で確かめるために取り分けたりんごが数個入っている写真。分類しきれないものを別の箱に取り分けることのメタファー](/images/ai-inquiry-triage/hero.jpg)

以下の数値は、すべて手元の生ログ（`codex exec --json` の出力と `-o` で保存した最終回答）を集計スクリプトにかけた結果から転記しています。メールは筆者が作った架空のもので、実在の顧客・物件は含みません。

## 先に結論

- 業務カテゴリだけの選択肢（JSON Schema の `enum`）では、AI は「当てはまらない」と言えません。あいまいなメール20回分は**0/20**しか人に回りませんでした（2モデルとも）。
- 理由（`reason`）の欄には「営業案内ですが、提示された分類では空室に関する項目が最も近いためです」のように、**当てはまらないと分かったうえで近い箱に入れた**と書かれていました。分かっていても、出口がないと箱に入れます。
- 「要確認」を `enum` に足すか、`needs_human` のような真偽値の欄を足すと、あいまいなメールの 75〜90% が人に回りました。はっきりしたメールの正解率は下がらず、誤って人に回した回数も 0 でした。
- 真偽値の欄（`needs_human`）を使う場合は、**category だけを見て振り分ける仕組みのままだと意味がありません**。この条件でも category は全件が業務カテゴリのどれかになり、クレームは修繕の箱に入ったままでした。

## なぜ「要確認」が要るのか

振り分けを自動化すると、メールは category の値でそのまま担当の受信箱に入ります。7分類だけで作ると、次のメールがどうなるかを考えてみてください。

- 「このままなら弁護士に相談して家賃の支払いも止めます。責任者から連絡してください」
- 「先日お話しした件、その後どうなりましたでしょうか」（何の件か本文にない）
- 「隣の部屋が夜中の2時までうるさい」（7分類のどれでもない）

7分類しかなければ、これらは修繕担当や物件案内の担当の受信箱に、ほかの定型メールと同じ顔で並びます。今回の実験では、まさにそうなりました。

## 実験の条件

| 項目 | 内容 |
|---|---|
| ツール | Codex CLI 0.163.0（`codex exec`、ChatGPT ログイン） |
| モデル | `gpt-6-luna`、`gpt-6.1-terra` |
| メール | 架空の不動産会社あて40通。はっきりしたもの30通（7分類に正解が1つ）、あいまいなもの10通（正解は「人が読むべき」） |
| 条件 | A: 7分類だけ／B: 7分類＋「要確認」／C: 7分類＋`needs_human`（true/false） |
| 回数 | 40通 × 3条件 × 2モデル × 2回 = 480回。1通ずつ別プロセスで実行 |
| 実行日 | 2026-10-30（JST） |

7分類は「内見予約」「空室・条件の問い合わせ」「賃料・初期費用の交渉」「申込・契約手続き」「入居中の不具合・修繕」「解約・退去」「売却・査定の相談」です。

あいまいな10通は、筆者が実験の前に「人が読むべき」と決めたものです。複数の担当にまたがる（退去の連絡＋原状回復費への異議、内見＋値下げ交渉、退去予定＋実家の土地の売却）、何の件か分からない、7分類にない（騒音の苦情、家賃の支払い遅れ、営業メール）、急ぎの人の対応が要る（法的措置をほのめかすクレーム、下の階への漏水）、の4種類です。このラベル自体が筆者の判断である点は、後の「限界」で触れます。

### 実行したコマンド

メール本文は標準入力で渡し、出力の形は `--output-schema` で固定しました。`codex exec` は、プロンプトの引数と標準入力の両方があると、引数を指示、標準入力を追加の文脈として扱います（[公式ドキュメント](https://developers.openai.com/codex/noninteractive)、取得日 2026-10-30）。

```bash
codex exec --json --ephemeral --skip-git-repo-check --ignore-user-config \
  -s read-only -m gpt-6.1-terra \
  --output-schema schema_B.json -o out.json \
  "$(cat prompt_B.txt)" < mail.txt
```

条件 B のスキーマです。条件 A は `enum` から「要確認」を除いたもの、条件 C は A に `"needs_human": {"type": "boolean"}` を足したものです。

```json
{
  "type": "object",
  "additionalProperties": false,
  "required": ["category", "reason"],
  "properties": {
    "category": {
      "type": "string",
      "enum": ["内見予約", "空室・条件の問い合わせ", "賃料・初期費用の交渉",
               "申込・契約手続き", "入居中の不具合・修繕", "解約・退去",
               "売却・査定の相談", "要確認"]
    },
    "reason": { "type": "string" }
  }
}
```

条件 B のプロンプトでは、7分類の後に「要確認」を並べ、次の1文を足しました。条件 C では、同じ4つの条件を `needs_human` を true にする条件として書きました。

```text
次のどれかに当てはまるときは「要確認」を選んでください: 複数の分類にまたがり担当が分かれる／何の用件か本文から分からない／上の7分類のどれにも当てはまらない／クレームや法的な話など人がすぐ読むべき内容。
```

## 結果

![棒グラフ。あいまいなメール10通×2回のうち人の確認に回せた回数。A（7分類だけ）は gpt-6-luna 0/20、gpt-6.1-terra 0/20。B（要確認を追加）は 15/20 と 18/20。C（7分類＋needs_human）は 17/20 と 16/20。はっきりしたメール30通×2回は全条件で60/60正解、誤って人に回した回数は0](/images/ai-inquiry-triage/fig1-flagged.png)

| 条件 | モデル | はっきりした30通×2回の正解 | そのうち誤って人に回した回数 | あいまいな10通×2回で人に回せた回数 |
|---|---|---|---|---|
| A: 7分類だけ | gpt-6-luna | 60/60 | 0 | 0/20 |
| A: 7分類だけ | gpt-6.1-terra | 60/60 | 0 | 0/20 |
| B: 「要確認」を追加 | gpt-6-luna | 60/60 | 0 | 15/20 |
| B: 「要確認」を追加 | gpt-6.1-terra | 60/60 | 0 | 18/20 |
| C: `needs_human` を追加 | gpt-6-luna | 60/60 | 0 | 17/20 |
| C: `needs_human` を追加 | gpt-6.1-terra | 60/60 | 0 | 16/20 |

C の「人に回せた回数」は `needs_human` が true だった回数です。480回すべて終了コード0で、スキーマに合わない出力はありませんでした。

### 条件 A：あいまいなメールはどの箱に入ったか

2モデル×2回の計4回とも、10通すべてが同じ箱に入りました。

| メール（要旨） | 入った箱（4回とも） |
|---|---|
| 「弁護士に相談して家賃の支払いも止めます」 | 入居中の不具合・修繕 |
| 下の階の天井に水のしみ、保険も分からない | 入居中の不具合・修繕 |
| 隣の部屋が夜中までうるさい | 入居中の不具合・修繕 |
| 「先日の件、その後どうなりましたか」 | 空室・条件の問い合わせ |
| 空室対策の Web 広告の営業メール | 空室・条件の問い合わせ |
| 退去予定＋実家の土地を売りたい | 売却・査定の相談 |
| 退去の連絡＋壁の穴の請求に納得できない | 解約・退去 |
| 内見したいが家賃が下がらないなら意味がない | 賃料・初期費用の交渉 |
| 家賃の支払いが遅れそう、分割にしたい | 賃料・初期費用の交渉 |
| 昨日の申込を取り消したい、申込金は返るか | 申込・契約手続き |

理由の欄を読むと、モデルは当てはまらないことに気づいていました。営業メールについては2モデルとも「営業案内ですが、提示された分類では空室に関する項目が最も近いためです」（gpt-6.1-terra、1回目）という趣旨を書き、「先日の件」については gpt-6.1-terra が「具体的な内容がなく、他の分類を判断できません」と書いたうえで「空室・条件の問い合わせ」を選んでいます。**`reason` に気づきが書かれていても、振り分けは category で行われるので、その気づきはどこにも届きません。**

### 条件 B・C：人に回らなかったもの

表の「分類」は、人に回さず7分類のどれかに入れた（C では `needs_human` が false だった）ことを指します。

| メール | B: gpt-6-luna | B: gpt-6.1-terra | C: gpt-6-luna | C: gpt-6.1-terra |
|---|---|---|---|---|
| 申込の取り消し・申込金の返金 | 2回とも分類 | 2回とも分類 | 2回とも分類 | 2回とも分類 |
| 家賃の支払い遅れ・分割 | 2回とも分類 | 人に回した | 人に回した | 2回とも分類 |
| 下の階への漏水 | 1回は分類 | 人に回した | 人に回した | 人に回した |
| 内見＋値下げ交渉 | 人に回した | 人に回した | 1回は分類 | 人に回した |

「申込の取り消し」は 8回すべて「申込・契約手続き」に入りました。これは筆者のラベルが厳しすぎた可能性があります。申込を扱う担当が取り消しも扱う会社なら、この振り分けで困りません。逆に「家賃の支払い遅れ」は、モデルと条件で結果が割れました。7分類のどれにもない、と書いたのに「賃料」という言葉に引っぱられて「賃料・初期費用の交渉」に入る回がありました。自社で使うなら、こうした**境界のメールを数通テスト用に用意して、どちらに入るかを先に見ておく**のが安全です。

条件 C で注意したいのは、`needs_human` が true のときも category は必ず7分類のどれかになることです。法的措置をほのめかすクレームは、C でも4回とも category が「入居中の不具合・修繕」、`needs_human` が true でした。振り分ける側のコードが `needs_human` を先に見るように作らないと、結果は条件 A と同じになります。

### 時間とトークン

1回あたりの実行時間の中央値は gpt-6-luna 3.4秒、gpt-6.1-terra 4.2〜4.4秒でした（条件で差はほぼなし）。出力トークンは中央値 49〜56 ですが、入力トークンは中央値で約1.4万（gpt-6-luna 13,968、gpt-6.1-terra 14,595）ありました。メール本文は数百字なので、入力の大半は Codex 側が毎回付ける指示です。1日に数百通を1通ずつ `codex exec` で回すと、利用枠の消費はメールの長さではなくこの固定分で決まります。大量に回すなら、API で直接呼ぶ構成のほうが向いています。

## 自社で作るときのチェックリスト

1. 分類の選択肢に「要確認」（または「その他・人が読む」）を必ず入れる。
2. 「要確認」にする条件を、プロンプトに具体的に書く（今回は「担当が分かれる」「用件が分からない」「どれにも当てはまらない」「クレームや法的な話」の4つ）。
3. 真偽値の欄で持つなら、振り分けのコードでその欄を category より先に見る。
4. 境界のメール（取り消し、支払いの相談、苦情など）をテスト用に数通作り、モデルを変えるたびにどこに入るかを確かめる。
5. `reason` は人が見る画面に出す。今回のように「当てはまらないが近いので」と書かれている回が、選択肢の作り方を見直す手がかりになります。

## 限界

- メールは筆者が作った架空の40通です。実際の問い合わせはもっと長く、署名や引用が混ざります。
- 「あいまい」のラベルは筆者が実験前に決めたもので、別の人が付ければ変わります（とくに「申込の取り消し」と「家賃の支払い遅れ」）。
- 各条件は2回ずつです。2回で結果が割れたのは、条件 B の gpt-6-luna（漏水のメール）と条件 C の gpt-6-luna（内見＋値下げ交渉）・gpt-6.1-terra（退去予定＋土地の売却で category が割れた。`needs_human` は2回とも true）の3か所でした。回数を増やすと割合は動きます。
- Codex CLI 経由の結果です。API で同じスキーマを使った場合は確かめていません。
